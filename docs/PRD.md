# WeMark 产品需求文档（PRD）

> 本文档是 WeMark 的**整体 PRD**，是所有需求的事实来源（Single Source of Truth）。
> 每个大需求对应一份子 PRD（位于 `docs/specs/`），随任务推进动态更新。

## 1. 概述

WeMark 是一款基于 Markdown 的桌面文本编辑器，核心差异在于：**以「聊天」的形式编辑 Markdown**。界面仿照 macOS 版微信，文档像聊天记录一样被切分成一个个「内容块」渲染；用户在底部编辑区输入、发送，渲染区即时呈现结果；点击任意内容块即可回到编辑区原位修改。

- **目标平台**：macOS（首要）、Windows、Linux。
- **参考项目**：[CatVinci-Studio/Textus](https://github.com/CatVinci-Studio/Textus)。

## 2. 目标 / 非目标

### 2.1 目标（Goals）

- 用「聊天式」交互大幅降低 Markdown 编辑的心智负担：**所见即所发，所点即所改**。
- 提供流畅、直观的**块级往返编辑**体验（本产品灵魂）。
- 完整支持 GFM 语法，并以 pele.js 高性能渲染 Mermaid 图表。
- 文档以本地 `.md` 文件存储，文档即文件、零迁移成本。

### 2.2 非目标（Non-goals，MVP 阶段不做）

- 实时多人协作 / 云端同步。
- 富文本（所见即所得）编辑，而非 Markdown 源码编辑。
- 移动端适配。
- 插件市场 / 第三方扩展体系。

### 2.3 反目标（Anti-goals）

- 不要退化成「左源码右预览」的传统分屏编辑器——聊天式块级交互是底线。
- 不要为了功能堆砌牺牲「直观、方便」这一核心体验。

## 3. 核心概念与术语

| 术语 | 含义 |
|------|------|
| **内容块（Block）** | 渲染区的最小可编辑单元，对应一个 Markdown 块级元素（标题/段落/列表/代码块/图片/表格/引用/Mermaid 图表等） |
| **文档（Document）** | 一个 `.md` 文件，由一组有序的内容块组成 |
| **编辑区状态** | `idle`（新建模式）或 `editing(blockId)`（编辑某个已有块） |
| **原位更新** | 对某个块的修改只替换该块内容，块在文档中的位置不变 |
| **草稿（Draft）** | 编辑区「有内容但未发送就离开」时自动保存的现场，含源码与编辑目标，可从工具栏草稿箱下拉恢复 |

## 4. 整体布局

仿 macOS 微信，从左到右四栏 + 底部输入区：

```
┌──────┬────────────┬──────────────────────────────┐
│ 功能 │  文档列表  │        渲染区（聊天记录区）      │
│  栏  │            │        [右上角工具栏]           │
│ (图标│  搜索框     │                              │
│ +设  │  ▸ 文档树   │   · 内容块1                  │
│  置) │  ▸ 置顶项   │   · 内容块2                  │
│      │  ▸ 文档项   │   · 内容块3 ...              │
├──────┴────────────┴──────────────────────────────┤
│                编辑区（聊天输入区）                   │
│           [Markdown 输入框]                        │
│           [底部工具栏：加粗/斜体/列表/代码/图片上传…]  │
└──────────────────────────────────────────────────┘
```

| 区域 | 职责 |
|------|------|
| **1. 功能栏** | 功能图标入口 + 设置入口 |
| **2. 文档列表栏** | 文档列表（支持置顶、树级展开），顶部搜索框（搜文档名 + 文档内容） |
| **3. 渲染区** | 渲染 Markdown 文档，右上角工具栏保留 |
| **4. 编辑区** | 编辑 Markdown 源码，底部工具栏提供常用格式快捷操作与图片上传 |

## 5. 核心交互设计：块级往返编辑 ⭐

> 这是 WeMark 的灵魂交互，需重点打磨，详细规范见子 PRD `docs/specs/03-block-editing.md`。

### 5.1 三种状态机

编辑区始终处于以下三种状态之一：

| 状态 | 触发 | 发送行为 |
|------|------|---------|
| `idle` | 初始 / 取消编辑 / 发送完成 | 新块**追加到文档末尾** |
| `editing(blockId)` | 点击某个内容块 | 修改**原位替换**该块 |

### 5.2 交互流程

**A. 新建块（idle）**
1. 用户在编辑区输入 Markdown 源码。
2. 点击「发送」（或快捷键 Enter）。
3. 解析源码 → 生成一个新内容块 → 追加到渲染区末尾。
4. 编辑区清空，回到 idle。

**B. 点击块 → 原位编辑 → 回归原位**
1. 用户点击渲染区某内容块。
2. 该块进入「正在编辑」视觉态（高亮/描边，类似微信被回复的消息）。
3. 该块的 Markdown 源码**回填**到编辑区；编辑区进入 `editing(blockId)`，底部出现「正在编辑第 N 块 · 取消」提示条。
4. 用户修改源码后点击「发送」（或 Enter）。
5. 该块在**原位置**更新渲染结果，退出高亮；编辑区清空回到 idle。

**C. 取消编辑**
- 点击「取消」（或 Esc）→ 编辑区清空回到 idle，块退出「正在编辑」态，源码与渲染均不变。

### 5.3 设计要点（直观、方便）

1. **单击即编辑**：点击块直接进入编辑，不做「先选中、再点编辑」的两段式，减少一步。
2. **明确的编辑目标提示**：编辑非末尾块时，编辑区上方始终显示「正在编辑：第 N 块」，避免用户误以为在追加。
3. **原位回归**：修改后的块保持在文档中的原位置，不跳动、不重排，保证空间记忆。
4. **键盘流**：Enter 发送 / Shift+Enter 换行 / Esc 取消，贴近微信聊天习惯。
5. **可预期的新增位置**：idle 状态发送永远追加到末尾；若要插入到中间，后续增强提供「块间插入点」。

### 5.4 MVP 范围边界

- ✅ 追加到末尾、点击块原位编辑、取消编辑。
- ✅ 单块编辑（一次只编辑一个块）。
- ✅ 草稿箱：未发送内容自动入草稿，工具栏下拉恢复（连同编辑目标），仅存内存。
- 🚫 拖拽排序块（后续）。
- 🚫 块间插入点 / 移动块（后续）。

## 8. 子 PRD 规范

- **位置**：`docs/specs/<两位编号>-<主题>.md`。
- **内容结构**：背景与目标 / 需求详述 / 交互与状态 / 验收标准 / 涉及任务 / 变更记录。
- **更新时机**：任务开始前细化、实现中补充、完成后回填验收结论。
- **命名**：编号与本文档第 6/7 节的模块编号保持一致。

## 9. 里程碑（按优先级）

1. **M0 — 可运行骨架**：T1 完成，能 `npm run tauri dev` 启动空窗口。
2. **MVP — 核心闭环**：T2~T6 完成，能新建/打开 `.md`，以聊天式块级编辑完成「写 → 发 → 渲染 → 点 → 改 → 原位回归」全流程。
3. **V1 — 体验完善**：T7~T9 完成，补齐工具栏、图片上传、文件管理与设置。
